# HarrTest 4.1 Gold validation

The live development test uses `gpt-6-luna` with **low** reasoning effort.
The short task asks, in Arabic, for a small keyboard-playable Three.js racing
game and delegates the design and rules. Both arms start with the same local
Three.js 0.180.0 files and Git scaffold tree
`651609df207ff32e170f19ce7187b5a898245714`.

## Attribution and experimental boundary

The observer changes the HarrTest harness, launches the original task,
inspects evidence and scores the output. Product code and product repair
instructions belong to Luna and its own native workers. Fresh isolated
coordinators use `fork_turns: none`; they cannot inspect sibling trials.
All observed model/effort contexts are checked against the declared settings.
Shared vendor dependencies are seeded equally by the runner.

An earlier development run received observer feedback about its scene. It is
retained as assisted development and excluded from the unaided result.
Later isolated trials receive the original task and common setup only.
Harness revisions and resumed verification are recorded separately from a
fresh generation. Failed and incomplete attempts are retained.

The observer's production-verification CLI call once created a temporary
host binding as a side effect. It was removed to restore the previous absent
state; no product file changed. Luna had already passed production checking
without that binding. Subsequent observer queries use the read-only Python API.

## Frozen browser procedure

The six dimensions each contain four observable items: rendering, controls,
car/track/environment, interface, variety/detail and integrated journey.
The maximum is 24. The frozen rubric SHA-256 is
`53239c7ecc48dfe72437d7c1164c34e32415dbeba75533d4ac99d608fffa77df`.
Use Edge 157.0.4341.46, ANGLE SwiftShader, 1440x900, DPR 1 and one renderer at a time.
Wait for a visible countdown when needed, hold acceleration for 2.6s, steer
right for 0.75s, brake for 0.9s, then exercise public completion/recovery/replay.
Retain screenshots, actual HUD readings, frame timing, errors and served hashes.
Never change hidden game state to manufacture a successful journey.

The native plain result was scored before viewing the final candidate.
It scores **20/24**: `3,4,3,3,3,4`. Public acceleration, steering, braking,
three-lap completion and replay work. Its absent contrasting road surface
and overlapping title/position glyphs lose points. The ready drive records
54 frames in 2619ms, about 20.6fps in the software renderer.

Acceptance for the later isolated candidate requires at least 21/24, all five
mandatory runtime outcomes, passed Team provenance/QA and usable timed
progress. Report the raw score, frame rate, elapsed generation time and all
attempts. A single task with harness revisions is development evidence,
not a general causal estimate of skill effectiveness.

## Controller checks

The existing 12-case controller comparison still accepts/rejects 12/12 as
expected, with 0 false accepts and 0 false blocks. The v3.2.2 fixture baseline
scores 4/12. These are deterministic real CLI decisions with fixture worker
identities, not live model quality measurements or an improvement over 4.0.
New Team tests reject review-only production, serial work, stale outputs,
coordinator ownership violations and early QA. Root/Builder regressions check
the optional Team binding and prevent milestone bypasses.

The complete local suite passed 288 tests with 4 environment-dependent skips.
The focused Team suite passed 15. Python 3.10 syntax and skill layout validation
also passed. Host hooks require actual loading and trust; installing the skill
alone does not turn its instructions into universal tool-level interception.
