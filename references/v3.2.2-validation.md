# v3.2.2: ordered concurrent evidence publication

Starting public source: v3.2.1, `bb8bff2e4abdd6b9d76f0740cb05b9af72792881`.
Its four Linux/Windows Python 3.10/3.12 CI jobs passed. The locally installed skill
was v3.1.0; it was inspected without silently replacing a running mission's checker.

## Reproduced general failure

Two real `proof.py run` processes used one sealed contract and unchanged source.
An older command waited while the newer command returned the wrong numeric result.
The newer collector failed, then the older successful collector finished and
unconditionally overwrote `latest/addition.json`. Current child verification could
then pass despite the newer failure. This is a collector ordering defect, independent
of programming language, model, host, application framework or adapter.

Both admission and conditional completion now use the same short SQLite critical
section. Latest means admission order, not wall time, random run ID, or finish order.
The command never runs inside the lock. Old receipts remain intact; unfinished
newer attempts continue to invalidate acceptance. Lock errors do not bypass it.

## Actual validation

Nine new regressions launch real collector/command processes and control their
completion with runtime barriers outside source scope:

- Older PASS/newer FAIL, and older FAIL/newer PASS, finished in reverse order.
- Three overlaps, interrupted collector, fresh restart and retained historical runs.
- Independent checks running while another command remains pending.
- A paused comparison excludes a separate admission process; a short lock timeout
  fails closed. Killing a lock owner permits recovery without deleting its file.
- A corrupt lock database prevents command execution instead of unsafe fallback.
- With both predecessor and integration freshly verified on unchanged source, the
  newer failure blocks child, root, workflow CLI and Builder acceptance. A later
  actual passing integration restores acceptance without changing the contract.

The separate native-host reviewer found and helped close an oracle gap: stale
predecessor evidence must not be the reason this last negative test passes. Its
independent Windows run also exposed a transient polling read/replacement conflict;
test polling now shares the publication lock and cleanup releases every owned
fixture command even if startup observation fails. These failures were fixed,
not skipped. No fake worker, separate provider or model client was used.

The complete suite also exercises the existing-code CLI persistence repair and the
greenfield HTTP API's real requests, invalid input, process restart, persistence,
cumulative milestones, clean ZIP installation and source-drift rejection. These
challenge generalization beyond the arithmetic fixture without claiming that
author-supplied applications were autonomously generated by a model.

## Limits

This fixes cooperative local collectors sharing task state on a filesystem with
working SQLite locking. It does not serialize application side effects, cancel
superseded commands, authenticate a hostile writer, support mixed collector
versions, or guarantee network-filesystem/distributed coordination. Runtime
resource ownership still belongs to the existing workflow. Relevant collector
changes invalidate old seals; follow the migration guide and preserve history.

No comparative live coding-agent trial or model-performance uplift was measured.
The native reviewer executed a real review and deterministic tests; that is not
a benchmark of improved autonomous coding, overnight operation or arbitrary
software correctness. Optional browser/simulator/model trials remain distinct.
